# Git коммит и push с безопасностью и AI-генерацией

Скилл для безопасной отправки изменений в удалённый репозиторий с автоматическим анализом, проверкой секретов и умным формированием сообщений. Выполняй **только** когда пользователь явно просит закоммитить и/или запушить.

## Разрешённые команды Git

### Диагностические (только чтение, БЕЗ изменений)

- `git status --porcelain` — список изменённых файлов (машиночитаемый формат)
- `git diff --name-only` — только имена изменённых/неотслеживаемых файлов
- `git diff --stat` — статистика изменений (+/- строк)
- `git diff --cached --name-only` — файлы в индексе (после add)
- `git branch --show-current` — текущая ветка
- `git rev-parse --abbrev-ref HEAD` — альтернативное получение ветки
- `git log -1 --format=%h` — хеш последнего коммита (только короткий)
- `git log -1 --format=%B` — сообщение последнего коммита
- `git remote -v` — список remote репозиториев (только для чтения)
- `git config --get branch.${branch}.remote` — upstream для ветки
- `git config --get branch.${branch}.merge` — upstream ветка

### Изменяющие (только эти!)

- `git add <пути...>` — добавление файлов в индекс
- `git commit -m "сообщение"` — создание коммита
- `git commit -m "заголовок" -m "тело"` — коммит с заголовком и телом
- `git push [remote] [branch]` — отправка коммитов

### Запрещены ВСЕГДА (без явного разрешения пользователя)

- `git reset`, `git rebase`, `git merge`, `git stash`
- `git commit --amend`, `git push --force`, `git push --force-with-lease`
- `git config` (изменяющая), `git remote` (изменяющая)
- `git cherry-pick`, `git revert`, `git bisect`
- `git add .` или `git add -A` (всегда указывай конкретные пути)
- `git pull`, `git fetch`, `git rm` и прочие команды вне списков выше

## Автоматические проверки безопасности (ОБЯЗАТЕЛЬНЫЕ!)

### Проверка на секреты перед add

Сканируй содержимое добавляемых файлов на наличие паттернов:

```regex
# Паттерны секретов (regex)
API_KEY|SECRET|PASSWORD|TOKEN|PRIVATE_KEY
AKIA[0-9A-Z]{16}  # AWS ключи
-----BEGIN RSA PRIVATE KEY-----
Bearer [a-zA-Z0-9_-]{20,}
```

**Файлы, которые всегда проверять:**

- `.env`, `.env.local`, `.env.*`
- `*.pem`, `*.key`, `*.p12`, `*.jks`
- `credentials.json`, `secrets.yml`
- `application-secrets.properties`

**Действие при обнаружении:**

```markdown
⚠️ ОБНАРУЖЕНЫ ПОТЕНЦИАЛЬНЫЕ СЕКРЕТЫ!

Файл: .env
Содержит: DATABASE_PASSWORD=admin123
⚠️ НИКОГДА не коммить секреты в git!

Действия:
1. Удалить файл из коммита
2. Добавить в .gitignore (пользователь — вручную, если правила проекта запрещают правку .gitignore агенту)
3. Использовать переменные окружения или vault

Коммит ОТМЕНЁН. Исправьте проблему и попробуйте снова.
```

### Проверка размера файлов

- **> 1MB:** предупреждение (может замедлить репозиторий)
- **> 5MB:** запрос подтверждения
- **> 10MB:** блокировка

### Проверка временных/бинарных файлов

Автоматически предупреждай и предлагай пропустить:

- `*.tmp`, `*.log`, `*.cache`, `*.class` (если не в .gitignore)
- `*.bak`, `*.old`, `*.orig`, `*.swp`
- `node_modules/`, `target/`, `build/`, `dist/`
- `*.exe`, `*.dll`, `*.so`, `*.dylib`

## Формирование сообщения коммита (AI-генерация)

### Язык и метка (ОБЯЗАТЕЛЬНО)

- **Весь текст коммита** (subject, body, footer), сгенерированный этим скиллом, пиши **на русском языке**.
- Описывай **что сделано** (совершённое действие, прошедшее время), **не** «что делать» (императив, инструкция).
- Сразу **после типа изменений** (и scope, если есть) добавляй метку **`[AI GENERATED]`** — для всех коммитов, созданных по этому скиллу.

**Формат subject:**

```text
<type> [AI GENERATED]: <subject>           # без scope
<type>(<scope>) [AI GENERATED]: <subject> # со scope
```

Примеры: `feat [AI GENERATED]: добавлена валидация email`, `fix(auth) [AI GENERATED]: обработан пустой токен`.

### Процесс генерации

1. Получи список изменённых файлов через `git status --porcelain`
2. Проанализируй типы изменений (добавление/удаление/модификация)
3. Сгенерируй сообщение по **Conventional Commits** (тип на английском, текст — на русском, с меткой `[AI GENERATED]`)

### Формат сообщения

```text
<type> [AI GENERATED]: <subject>
<type>(<scope>) [AI GENERATED]: <subject>

<body на русском>

<footer на русском при необходимости>
```

### Типы изменений (определяй автоматически)

| Тип | Когда использовать | Пример |
|-----|-------------------|--------|
| feat | Новая функциональность | `feat(user) [AI GENERATED]: добавлена валидация email` |
| fix | Исправление бага | `fix(auth) [AI GENERATED]: обработан пустой токен` |
| docs | Документация | `docs [AI GENERATED]: обновлена инструкция по установке` |
| style | Форматирование (без логики) | `style [AI GENERATED]: отформатирован код` |
| refactor | Рефакторинг | `refactor(service) [AI GENERATED]: вынесен валидатор` |
| test | Добавление/изменение тестов | `test(user) [AI GENERATED]: добавлены граничные случаи` |
| chore | Зависимости, конфиги | `chore [AI GENERATED]: обновлены зависимости` |
| perf | Производительность | `perf(query) [AI GENERATED]: добавлен индекс` |
| ci | CI/CD конфигурация | `ci [AI GENERATED]: добавлен GitHub Actions` |

### Правила формирования

- **subject:** на русском, не более 72 символов, **что сделано** (прошедшее время / результат), без точки в конце, обязательно с `[AI GENERATED]` после типа; **не** используй императив («добавить», «исправить»)
- **body:** на русском, перечисляет **сделанное** (прошедшее время), объясняет зачем было изменение; каждое предложение с новой строки
- **footer:** на русском при необходимости: `Closes #123` или `BREAKING CHANGE: описание`

### Пример генерации

**Анализ изменений:**

```text
M src/main/java/UserService.java (+47, -12)
A src/main/java/EmailValidator.java (+35, -0)
M src/test/java/UserServiceTest.java (+28, -3)
```

**Сгенерированное сообщение:**

```text
feat(user) [AI GENERATED]: добавлена валидация email при создании пользователя

- Реализован компонент EmailValidator с regex-проверкой
- Интегрирована валидация в UserService.createUser()
- Добавлена обработка ошибок через BusinessException
- Покрыты граничные случаи unit-тестами

Closes #234
```

## План выполнения

### Фаза 1: Анализ (обязательно)

```bash
git status --porcelain
git branch --show-current
git diff --stat
git diff --name-only
```

Проанализируй вывод:

- Список изменённых файлов
- Есть ли секреты/большие файлы
- Нужно ли подтверждение

### Фаза 2: Подготовка (с проверкой)

```bash
git add <file1> <file2> <file3>  # конкретные пути, не . и не -A
```

Проверь:

- Нет ошибок при добавлении
- Файлы с секретами не добавлены
- Размер добавленных файлов приемлем

### Фаза 3: Коммит (с AI-сообщением)

```bash
git commit -m "feat(scope) [AI GENERATED]: кратко что сделано" -m "- Сделанный пункт 1" -m "- Сделанный пункт 2"
```

### Фаза 4: Push (с проверкой)

- Если есть upstream: `git push`
- Если новая ветка: `git push -u origin <branch>`
- Если указал пользователь: `git push <remote> <branch>`

**При любой ошибке, предупреждении или конфликте в выводе `git push`** — немедленно прекрати операции скилла и передай управление пользователю (см. раздел «Ошибки при push»). Не повторяй push и не выполняй другие git-команды.

## Чеклист безопасности перед выполнением

Перед **КАЖДЫМ** коммитом проверь:

- [ ] Не добавляются ли файлы с секретами (пароли, ключи, токены)
- [ ] Нет ли больших бинарных файлов (>1MB)
- [ ] Не добавляются ли временные/скомпилированные файлы
- [ ] Сообщение на **русском**, с **`[AI GENERATED]`**, формулировка **что сделано** (не императив / не «что делать»)
- [ ] Пользователь подтвердил, если >3 файлов или >100 строк изменений

Если любой пункт не пройден — **ОСТАНОВИСЬ** и запроси подтверждение!

## Ошибки при push (критично)

Если во время **`git push`** возникла **любая** ошибка, предупреждение (warning) или признак конфликта (включая non-fast-forward, rejected, permission denied, network error, hook failure):

1. **Немедленно прекрати** все операции скилла — не делай повторный push, не выполняй `fetch`/`pull`/`rebase`/`merge`/`force`.
2. **Передай управление пользователю** — кратко опиши ситуацию и приложи **полный текст** stderr/stdout команды `git push` без сокращений.
3. **Не предлагай** автоматически исправлять конфликт — только факты и вывод git; дальнейшие шаги решает пользователь.

**Шаблон ответа:**

```markdown
❌ Push не выполнен. Операции скилла остановлены.

**Команда:** `git push ...`
**Код выхода:** (если известен)

**Вывод git:**
```
<полный текст ошибки/предупреждения>
```

Дальнейшие действия выполните вручную или дайте новую инструкцию.
```

### Примеры ситуаций при push (только остановка и передача пользователю)

**Push rejected (non-fast-forward):** приложи вывод `remote: error: failed to push...` — не предлагай `pull`/`rebase`/`force` от имени скилла.

**Нет upstream / unknown branch:** если `git push` завершился ошибкой — остановись и передай вывод. Если upstream ещё не настроен, **до** push можно диагностировать через `git config --get` и **спросить** пользователя, выполнять ли `git push -u origin <branch>` — но после неудачного push только передача управления.

## Обработка ошибок до push

### Git add не нашёл файл

- Проверь существование файла через `Read` / `Glob`
- Предложи правильный путь (от корня репозитория)
- Не добавляй частично — отмени операцию

## Защита критических веток

**Ветки, требующие подтверждения:**

- `main`, `master`, `develop`
- `release/*`, `prod/*`, `production/*`

**Действие при push в эти ветки:**

```markdown
⚠️ ВНИМАНИЕ! Push в защищённую ветку: main

Это может повлиять на production/CI/CD системы.

Подтвердите push:
- Ветка: main
- Коммиты: 3 коммита (47 добавлений, 12 удалений)
- Remote: origin

Продолжить? (y/N)
```

## Ограничения и стоп-условия

**НЕ ВЫПОЛНЯЙ и НЕ ПРЕДЛАГАЙ:**

- Создание **Merge Request** (MR) или **Pull Request** (PR) — ни через `gh`, ни через API, ни в ответе пользователю после push

**НЕ ВЫПОЛНЯЙ команду, если:**

- Пользователь явно не попросил коммит/push (даже если есть изменения)
- В списке изменений есть файлы с секретами
- Не удалось определить ветку или remote (спроси)
- Требуется подтверждение, но пользователь его не дал
- После `add` / `commit` возникла ошибка (не пытайся исправить автоматически)
- После **`git push`** — любая ошибка/предупреждение/конфликт: **немедленная остановка** и передача управления с полным текстом вывода (без повторных попыток и без «починки» от скилла)

**ВАЖНО:** Показывай пользователю **ЧТО** будешь делать и запрашивай подтверждение для опасных операций (push в `main`, коммит секретов). Коммиты — **на русском**, **`[AI GENERATED]`**, текст **что сделано**. **Не создавай MR/PR.**

**Правила проекта:** если действуют workspace-правила (например, запрет правки `.gitignore` агентом) — не нарушай их; предложи пользователю выполнить шаг вручную.

## Пример полного сеанса

**Пользователь:** «Закоммить изменения и запушь в develop»

**Анализ:**

```bash
git status --porcelain
# M src/main/java/UserService.java
# M src/test/java/UserServiceTest.java
# ?? .env

git branch --show-current
# feature/user-validation
```

**Обнаружение секретов:**

```text
⚠️ .env содержит DATABASE_PASSWORD!
Коммит отменён.
```

**Пользователь:** «Ок, удалил .env из коммита»

**Повторный анализ:**

```bash
git status --porcelain
# M src/main/java/UserService.java
# M src/test/java/UserServiceTest.java
```

**Выполнение:**

```bash
git add src/main/java/UserService.java src/test/java/UserServiceTest.java
git commit -m "feat(user) [AI GENERATED]: добавлена валидация email" -m "- Добавлен компонент EmailValidator" -m "- Интегрирована валидация в UserService" -m "- Добавлены unit-тесты"
git push -u origin feature/user-validation
```

**Ответ (успех):**

```markdown
✅ Успешно!
Коммит: f3a2c1d (feat(user) [AI GENERATED]: добавлена валидация email)
Изменения: 2 файла, +71 строка
Ветка: feature/user-validation → origin/feature/user-validation
```

**Если push завершился с ошибкой** — не продолжай сеанс; передай пользователю полный вывод `git push` по шаблону из раздела «Ошибки при push».

---

**Помни:** безопасно сохранить изменения в git. Коммиты — **на русском**, **`[AI GENERATED]`**, **что сделано** (не императив). **Не создавай MR/PR.** При сбое **push** — стоп и полный вывод пользователю.
