1. Тебе РАЗРЕШАЕТСЯ редактировать только файлы с расширениями: .java, .xml, .yml, .properties
2. Код должен быть легко читаемым, эффективным, поддерживаемым и масштабируемым
3. ВСЕГДА перед изменением существующего кода анализируй его влияние на связанные классы
4. НЕ ИСПОЛЬЗУЙ Deprecated классы, методы и конструкции
5. ВСЕГДА ПРИ НАПИСАНИИ кода придерживайся подхода TDD

# ЗАПРЕЩЕНО (никогда не используй):
- Необработанные checked exceptions (всегда оборачивай в BusinessException/RuntimeException)
- Сырые типы (raw types): List<String> вместо List
- конкатенация строк - используй StringBuilder
- null возврат из методов - всегда Optional или пустую коллекцию
- Статические мьютексы/синхронизация в веб-приложениях
- System.out.println - всегда логгер (Slf4j)

## Подход TDD, правила написания тестов
1. СНАЧАЛА напиши тест (JUnit 5 + Mockito). Для сложных интеграционных и end-to-end тестов и тестирования классов, с большим количеством инжектируемых компомнентов ОБЯЗАТЕЛЬНО ИСПОЛЬЗУЙ Spring Boot тесты. Если сомневаешься, использовать Spring-тесты или нет - спрашивай у пользователя, не гадай!
2. Убедись, что тест падает (красный). Если тест, написанный для новой бизнес-логики не падает - это ПЛОХОЙ тест ОБЯЗАТЕЛЬНО ЕГО ПЕРЕДЕЛАЙ! 
3. Напиши минимальный код для прохождения (зеленый). Если тесты падают - ИСПРАВЛЯЙ код, НЕ тесты!
4. Рефакторинг бизнес-логики (только после зеленого теста)

***Дополнительно***:
- не вызывай через Reflection API приватные методы, для их тестирования. Проверяй функциональность приватных методов через вызов связанных публичных методов
- избегай дублирования проверок - если сомневаешься, стоит ли покрывать кейс - спрашивай у пользователя, не гадай!
- для каждого теста используй @DisplayName с описанием теста на русском языке, помещай аннотацию после @Test
- Используй @ParameterizedTest КОГДА: одна и та же логика с разными входными данными, Edge cases и граничные значения, тестирование бизнес-правил с разными комбинациями
- НЕ тестируй конструкторы, Lombok-генерируемые методы, простые геттеры/сеттеры

## Требования по чистому коду
1. Следуй принципам SOLID
- S - класс имеет ТОЛЬКО одну ответственность и выполняет ТОЛЬКО одну задачу
- O - открыт для расширения, закрыт для изменений
- L - подтипы заменяемы
- I - интерфейсы минималистичны
- D - зависимости через абстракции
2. Именование: существительные для классов (UserRepository), глаголы для методов (calculateTotal). Если для именования класса или метода требуется несколько глаголов - класс или метод нарушает SRP, его надо декомпозировать
3. Комментарии: ИСПОЛЬЗУЮТСЯ ТОЛЬКО ДЛЯ
- сложной бизнес-логики
- для всех публичных методов интерфейса
- для всех публичных методов контроллеров
- констант и Enum
- метрик
Над методами и классами используй JavaDoc, внутри методов - комментарии через двойной слэш ("//")
4. Null Safety: всегда используй Optional, @NotNull/@Nullable аннотации
5. Stream API: предпочитай streams циклам для коллекций
6. НИКОГДА НЕ ИСПОЛЬЗУЙ package-private модификатор, всегда явно указывай модификаторы `public`, `private` или `protected`
